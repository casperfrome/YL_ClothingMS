    先认识你正在开发的系统

    从一次“保存品类”出发，确定浏览器、Java 程序和数据库各自做什么。

    你已经会语法，接下来要学的是协作方式

    会写类、方法和循环，解决的是“一个程序内部怎样计算”。开发后端接口还需要回答：程序怎样接收外部输入？别人怎样知道应该传哪些数据？数据怎样保存到下次启动之后？出错时怎样让调用者理解？本手册用 YL 商品管理后台逐步回答这些问题。阅读时不要求你预先懂 Servlet、设计模式、数据库框架或 Spring 注解；遇到的概念会在第一次使用时解释。

    这个项目管理服装商品、品类、配色、尺码、销售渠道、用户和模拟订单。品类是“针织衫、外套”这样的分类；一个商品款式属于一个品类，一个款式可以有多个配色，一个配色再有多个尺码。SKU 表示一个具体的款、色、码组合，而不同渠道上的售价和上下架状态放在销售记录中。先分清业务名词，才能决定数据库和接口应该表达什么。

    三处运行环境，不要混为一谈

    浏览器运行 HTML、CSS 和 JavaScript，负责展示页面、收集输入、发起请求。Java 后端作为独立进程运行，接收请求、判断业务规则并访问数据库。MySQL 又是一个独立的服务，负责保存数据和执行 SQL。它们即使都运行在你的电脑上，也通过明确的接口通信，不能直接读取彼此的局部变量。

    浏览器
    收集名称    → HTTP →Java 后端
    校验并处理    → SQL →MySQL
    持久保存

    点击“新增品类”时，浏览器先取得输入框的值，JavaScript 把它转为 JSON，再发送到后端。后端将 JSON 转成 Java 对象，校验名称，把名称写入 category 表，再把生成的编号和名称返回。浏览器收到结果后刷新品类列表。按钮只是整个流程的入口，真正决定“能否创建”的规则必须由后端执行，因为调用者也可以绕过页面直接发送请求。

    接口是双方的约定

    HTTP 接口由请求方法、地址、输入、输出和错误约定共同组成。“调用接口”就是按照这些约定发送请求。Java 的 interface 则是一种语言类型，用来声明方法契约。两者都叫接口，却处于不同层面。CategoryController 的一个普通 Java 方法可以处理 HTTP 接口；CategoryMapper 的 Java interface 则由 MyBatis 提供代理实现。

    Spring 是管理对象、依赖、事务等能力的基础框架。Spring MVC 在它上面处理 Web 请求和响应。Spring Boot 帮你根据依赖与配置把常用组件装配起来，并提供便捷的启动方式。MyBatis 把 Java 方法与 SQL 连接起来。MySQL 最终执行 SQL。它们不是互相替代的五种开发方案，而是这个项目不同位置的组件。

    阅读和操作方式

    建议第一次按章节顺序读，每章先理解目的，再看代码，再完成自测。第二次打开 IDE，沿着同样的顺序定位真实文件。教材中的“项目原始源码”来自本次制作时的项目快照；“教学展开”是为了降低语法密度的等价或局部示意；“练习新增”则是尚未接入项目的作业。不要把三者全部复制进工程，否则会造成重复类或重复路由。

    每一章都能离线阅读。页面中的流程演示只改变浏览器内的教学状态，不会运行 Java 或访问数据库。真正发请求的命令集中在联调章节。你可以先学完基础，再启动后端验证，遇到暂时不懂的地方用左侧搜索回到对应概念。

    把需求写成可以验证的接口契约

    先决定输入、结果和失败行为，再开始创建类。

    从一句话需求拆出规则

    “可以新增品类”还不够具体。开发前应追问的是：名称是否必填？是否允许重名？最长多少？创建成功返回什么？当前项目已经给出答案：名称不能空白，长度最多六十，保存前去掉两端空白，数据库限制名称唯一，成功返回生成的 ID 和保存后的名称。先把这些写清楚，你才知道 DTO、Service 和数据库分别需要承担哪些工作。

    请求方法表示操作意图。GET 通常读取数据，POST 在集合下创建资源，PATCH 修改资源的部分内容，DELETE 删除资源。它们不能只靠 URL 猜测：同一个 /api/categories，GET 和 POST 会映射到不同的方法。浏览器地址栏发起的是 GET，所以在地址栏输入新增接口地址不会自动调用 create。

    POST /api/categories HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{"name":"  针织衫  "}

    上面第一行由方法、路径和协议版本组成。Host 指明请求的主机，Content-Type 描述请求体的格式，空行之后才是 JSON。JSON 的属性名和字符串值要用双引号，不能把 JavaScript 对象写法或 Python 字典原样发送。localhost:8080 是服务地址，/api/categories 才是应用内的资源路径。端口改变不意味着 Controller 的路径也要改。

    HTTP/1.1 201 Created
Content-Type: application/json

{"data":{"id":5,"name":"针织衫"}}

    ID 五只是举例，不能在测试里断言每次都会得到五。数据库可能已经有数据，失败的插入或回滚也可能使自增序列留下空缺。201 表示创建成功；200 表示一般成功；204 表示成功但没有响应体。状态码属于 HTTP 响应，而 data、code、message 这些字段是项目自己选择的 JSON 结构，两者不要混淆。

    现有操作成功结果典型失败
    GET /api/categories200，列表含 productCount数据库不可用时可能 500
    POST /api/categories201，id 与 name400 校验失败；409 冲突
    PATCH /api/categories/{id}200，改名后的品类400、404、409
    DELETE /api/categories/{id}204，无响应体404 不存在；409 仍被使用

    失败也是正式契约

    空白名称应返回 400，重复名称应返回 409，修改不存在的资源应返回 404。这样前端可以将错误放在表单旁，而不必猜测成功响应中的某段文字。当前项目失败响应直接包含 code、message、fieldErrors，没有外层 data；删除成功甚至没有 JSON。客户端必须按实际状态处理，不能对所有响应无条件调用 JSON 解析。

    接口契约通常写入 OpenAPI，当前项目的 docs/openapi.json 就是机器可读说明。它能让工具知道地址、输入和返回结构，但文档不会自动保证实现正确，仍需要测试。新增字段时要同步思考调用方是否受影响：新增可选输出往往比较温和，改名、改类型、改状态码则可能让已有页面失效。

    一个很实用的方法是先列验收例子：正常名称、名称两端有空格、全空白、超长、重复。它们不是写完代码后随意试试，而是反过来指导设计。判断规则是否完整时，关注用户能观察到的行为，不要只检查“这个方法有没有被调用”。后面每一层都会对应这些例子中的一部分。

    设计项目结构：每段代码应该放在哪里

    沿着依赖方向划分职责，而不是机械地创建很多文件夹。

    先读项目根目录

    pom.xml 是 Maven 项目的构建说明；src/main/java 放参与正式运行的 Java 源码；src/main/resources 放运行资源；src/test 放测试源码和测试配置；target 是编译、测试、打包产生的结果。docs 保存文档，data/uploads 保存用户上传的图片。target 下的文件会在 clean 时被删除，因此不要到 target/classes 修改代码，也不要把需要长期保留的上传数据放进去。

├─ src/main/java/com/yl/clothing/
│  ├─ Application.java
│  ├─ controller/  service/  mapper/
│  ├─ entity/      entity/projection/
│  ├─ dto/         vo/       converter/
│  └─ common/      exception/ config/ enums/
├─ src/main/resources/
│  ├─ application.yml

│  └─ static/          # 页面、JS、CSS、示例图片

├─ src/test/resources/ # 测试库配置
├─ docs/
├─ data/uploads/
└─ target/            # 可重新生成的构建结果

    分层解决的是修改范围问题

    Controller 知道 HTTP：路径、参数从哪里来、状态码怎样返回。Service 知道业务：数据是否存在、是否允许操作、多次写入怎样组成一个工作单元。Mapper 知道数据访问：调用哪条 SQL、把结果映射成什么对象。Converter 决定对外字段。这样的划分使“改 SQL”通常不必改路由，“改页面参数”也不必把网络代码塞进数据库访问层。

    本项目约束 Controller 只依赖 Service，Service 不依赖 Controller、ApiResponse 或 ResponseEntity，Mapper 不依赖 Service、Controller 或 VO。这些约束在 ArchitectureTest 中被自动检查。返回方向不等于依赖方向：Mapper 可以把对象返回给 Service，但不需要持有 Service 并调用它。理解这一点，比记住“分三层”这个口号更重要。

    问题放置位置原因
    POST 路径、201 状态controllerHTTP 协议细节
    名称长度、必填dto输入数据约束
    有商品使用时不能删除service业务规则，需要查询和判断
    按 ID 查询、插入 SQLmapper + XML数据库访问
    隐藏 deleted 等内部字段converter + vo定义对外展示数据
    统一错误格式exception + common跨接口复用的约定

    包名、目录和扫描范围

    CategoryController 文件位于 controller 目录，并声明 package com.yl.clothing.controller。完整类名就是包名加类名。Application 放在 com.yl.clothing 根包，使其默认组件扫描能覆盖下面的业务包。如果把新类放到不相关的顶层包，仅仅文件存在并不意味着 Spring 会发现它。IDE 能编译一个类，与 Spring 能把它注册成 Bean，是两个不同的检查。

    resources/mapper 是运行时加载的 XML 资源，不是 Java 包。src/main/resources 本身不出现在 classpath 路径前缀里，因此配置写 classpath:mapper/*.xml。打包后 XML 和 YAML 会进入 JAR 内的运行资源区域，不需要源码目录仍然存在。与之相反，data/uploads 是项目选择的外部目录，其位置与运行工作目录有关。

    为什么这里没有 ServiceImpl

    Java interface 可以用于多实现、替换边界或稳定抽象，但不是分层的入场券。当前 CategoryService 只有一个业务实现，用一个具体类已经足够清楚。额外创建只有同一组方法的接口与 Impl 会增加新手跳转成本。以后真的存在多个策略或明确的模块边界，再引入抽象。不要把网上某个模板的文件数量当成规范程度。

    按业务领域分包也是合理选择，例如 category 下再包含自己的 Controller 和 Service。当前项目采用按技术职责分包，已经有对应测试，因此教材沿用它。学习目标是能解释依赖和边界，而不是证明所有项目只能使用这一种目录结构。Spring Boot 的结构建议也强调根包位置，并不强制本项目这些目录名。

    先验证工具，不从报错中猜环境

    理解对象是谁创建的：Bean、IoC 与注入

    把“框架魔法”还原成对象创建、连接和方法调用。

    先想象完全不用 Spring

    如果有一个普通 CategoryService，其构造器要求 CategoryMapper，那么创建它之前必须先得到 Mapper。创建 Controller 又必须先得到 Service。假设每个类都在内部自己 new 依赖，配置会分散，对象生命周期也很难统一管理。Spring 的核心作用之一就是集中管理这些对象及它们之间的关系，让业务类声明“我需要什么”，而不是自己寻找并创建所有协作者。

    // 原理示意：mapper 是已经准备好的数据访问实现
CategoryService service = new CategoryService(mapper);
CategoryController controller = new CategoryController(service);

    这里的示意展示的是依赖连接关系，不是本项目实际启动代码。尤其不能写 new CategoryMapper()，因为它是接口。真实运行时 MyBatis 的整合组件提供代理，Spring 再把这个代理注入 Service。你在 IDE 搜索不到一个手写的 CategoryMapperImpl，并不意味着实现缺失。

    Bean 不是一种特殊 Java 语法

    一个对象被 Spring 容器创建或注册并管理，就称作 Bean。类仍然是普通 Java 类，对象仍然有字段和方法。IoC 常译为控制反转，落到本项目就是把对象的组装控制交给容器。依赖注入是实现这种组装的方式之一：容器把 CategoryService 传入 Controller 的构造器，把 CategoryMapper 传入 Service 的构造器。

    // 来自 CategoryService 的构造器
private final CategoryMapper mapper;

public CategoryService(CategoryMapper mapper) {
    this.mapper = mapper;
}

    private 控制外部不能随意访问字段；final 表示这个引用在构造之后不能再次赋值；this.mapper 指当前对象的字段，右侧 mapper 指构造器参数。final 并不让 Mapper 内部全部状态自动变成不可变，也不等于事务锁。把语言层的作用与框架层的作用分开，能少记很多错误的“经验规则”。

    当前类只有一个构造器，所以通常不需要额外标注 @Autowired。构造器注入让依赖显式可见，普通单元测试也能手动传入替身。@Service 是用于标识服务组件的注解；@RestController 标识 Web 控制器；@Mapper 是 MyBatis 的映射接口标记，由相应扫描和整合机制注册。它们都需要运行环境处理，并非写上注解后 JVM 自己就会执行数据库操作。

    从创建对象到代理对象

    你获得的 Service 引用有时指向框架创建的代理，代理在调用真实业务方法前后加入事务等行为。正常代码仍然调用 service.create，业务类不必手写 begin 和 commit。这也是为什么自行 new 一个带 @Transactional 的类不能自动获得容器事务管理：它绕过了那条装配和拦截路径。Mapper 的代理则负责根据方法标识找到映射 SQL，是另一个用途的代理。

    默认情况下，Spring 管理的这类组件通常是单例 Bean，一次应用上下文里共享同一个实例。请求却可能由多个线程同时处理。所以 Controller 和普通业务 Service 应把每次请求的数据放在方法参数、局部变量中，不要把当前用户名称、当前请求 DTO 存进可变实例字段。构造器保存稳定依赖是合理的；保存临时请求状态则可能串数据。

    遇到注入失败怎样定位

    找不到 Bean 时，检查类上是否有合适的组件标记、是否位于扫描范围、依赖是否存在、Mapper 扫描是否生效。找到多个候选 Bean 时，则要指定具体实现或明确选择策略。依赖构成环时，应该先审视职责设计，而不是立刻开启循环依赖。当前品类链路是单向的，没有必要让 Mapper 反向调用 Service。

    学完本章，你应该能把“框架帮我做了”替换成更具体的描述：容器发现组件、解析构造器依赖、准备 Mapper 代理、注入依赖，最后 Web 框架调用 Controller 方法。这样后面遇到空指针、缺 Bean 或事务不生效时，才知道应该检查哪一段。

    先设计数据：表、约束与迁移

    让数据库表达最基本的不变量，并记录结构怎样演进。

    从业务名词提取表和字段

    品类需要稳定标识和可展示名称，因此 category 表只有 id、name 两个主要字段。不能直接用名称当作所有关联的标识，因为名称允许修改，商品如果引用名称就需要跟着改。使用独立主键后，改名只影响一行，商品仍然引用同一个 ID。设计字段之前先考虑“哪些属性会变化，哪些身份应该稳定”，比先选数据库框架更重要。

    CREATE TABLE category (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(60) NOT NULL UNIQUE
);

    BIGINT 对应较大整数，Java 用 Long 或 long 表示。PRIMARY KEY 标识唯一的一行，AUTO_INCREMENT 让数据库分配编号。VARCHAR(60) 限制字符串长度，NOT NULL 防止数据库空值，UNIQUE 防止违反数据库比较规则的重复名称。NOT NULL 不会拒绝空字符串或纯空格；UNIQUE 也不是 Java 的 equals，其大小写和部分字符比较行为还受数据库排序规则影响。

    所以“名称相同”应以实际数据库约束为最终裁决。你可以在 Service 先查询以便给出更友好的提示，但两个并发请求可能都先查到不存在，然后同时插入。只有数据库唯一约束能在这条写入边界保证不出现两个违反规则的记录。新增失败通常被转成冲突响应，而不是假装成功。

    关联关系与物理删除

    product 表的 category_id 通过外键指向 category.id。外键告诉数据库：引用的品类必须存在。品类和商品不是两个互不相干的列表，因此删除品类不能只执行一条 DELETE 就结束。Service 会先判断是否还有未删除商品使用它；仍有使用就拒绝。即使先检查过，数据库约束仍是并发变化时的最后一道保护。

    商品采用逻辑删除，即将 deleted 设为一，行本身还在。品类则执行物理删除。历史 V1 中商品的 category_id 不允许为空，后来 V3 将其改为允许 NULL，以便释放已删除商品对品类的引用。当前最终结构应结合所有迁移理解，不能只看第一份建表 SQL 就断言 category_id 永远不能为 null。

    package 确定类属于哪个包，import 引入校验注解，public record 定义对外可见的数据类型，name 是一个 String 组件。@NotBlank 要求值非 null、不是空串且含非空白字符；@Size(max=60) 限制长度，但它本身允许 null，所以两个注解承担不同工作。新增请求如果只写 @Size，字段缺失时并不会自动获得“必填”约束。

    不要把清理与校验的顺序讲反

    项目在 Service 中调用 name.strip()，发生在 DTO 校验之后。这意味着长度检查针对原始输入。例如六十个普通字符外面再加两个空格，虽然去空格后长度正好六十，当前请求仍先因原始长度六十二而失败。这里只解释现有行为，不偷偷把教材里的实现改成“先去空格再校验”，否则读者实际调用时会得到不同结果。

    strip 返回一个处理后的 String，不会原地修改已有 String。Java 字符串不可变，你必须使用它的返回值。不要把 strip 理解成能识别所有视觉上的空白字符；校验库和 Java 的空白判定有具体规则。初学阶段以普通空格、空字符串和常见中文名称验证即可，面向复杂国际化输入时再单独设计规范。

    错误提示从哪里来

    DTO 没有为这两个注解自定义 message，默认提示会受校验器和语言环境影响。因此测试不应死记某个英文句子，而应断言 HTTP 400、fieldErrors 包含 name、数据库未新增数据。全局异常处理器会把字段错误整理为 Map<String,String>。一个字段违反多条规则时，当前 Map 最终保存的是其中一个消息，不承诺所有消息或顺序。

    基础校验只处理结构与格式。名称是否重复需要考虑数据库状态，不存在的品类 ID 也需要查询；这些不应该被误写成一个只看字符串的注解。把校验放在正确位置后，失败发生在哪里就容易预测：JSON 解析前后、Controller 方法调用前、Service 业务判断中、数据库执行时，各有不同证据。

    CategoryMap 的 type 指向实体类型；column 指数据库结果集里的列标签；property 指 Java 属性。id 列放到 id 属性，name 列放到 name 属性。这里 autoMapping=false，意味着以显式映射为准。CategorySummaryMap 又额外映射 productCount，因为列表 SQL 多查了一个聚合值。resultMap 的 id 是映射配置的名称，和实体里的 id 字段不是同一种 ID。

    从网络到方法的最后一层

    内嵌 Web 服务器接收请求，Spring MVC 的 DispatcherServlet 协调查找处理方法、解析参数、执行方法、转换响应等步骤。你通常不用为每个接口编写 Servlet。路由查找失败和业务数据不存在都可能表现为 404，但前者是找不到入口，后者是进入正确入口后发现目标记录不存在，应通过路径、日志和错误消息区分。

    方法返回不等于浏览器已经收到响应。事务通常在 Service 代理返回时完成，Controller 再包装，最后才进行 HTTP 序列化和传输。若网络在提交后断开，数据库可能已经保存成功，调用者却没拿到结果。因此真实业务里“重试是否会重复创建”需要独立设计；当前品类接口通过唯一名称拒绝重复，不提供通用的请求幂等键机制。

    理解事务：什么时候提交，什么时候回滚

    把多次数据库操作视为一个整体，并理解注解生效的调用边界。

    先用失败场景解释事务的价值

    设想创建一个配色：先插入配色行，再插入五个尺码 SKU，再创建四个渠道的二十条销售记录。如果第二步或第三步失败，而前一步已经独立提交，就留下不完整的数据。事务让这些写入形成一个工作单元，要么在成功时一起提交，要么在失败时撤销未提交的修改。它不能自动修正业务算法，但能避免中间状态被当成最终成功。

    在当前 CategoryService.create 上，@Transactional 包围插入和回读；在 createColor 上，它包围多表写入。事务边界放在业务方法通常更合适，因为 Service 知道“一次操作”包含哪些数据库动作。若每个 Mapper 方法各自提交，即使都执行成功过一部分，也无法在后续失败时统一撤回已提交的前半段。

    进入 Service 代理→开启或加入事务→业务方法与 SQL→提交 / 回滚

    默认规则要说准确

    使用当前工程的默认 Spring 事务规则时，运行时异常和 Error 会触发回滚；受检查异常并非默认都触发回滚，可以通过 rollbackFor 等配置明确要求。BusinessException 是 RuntimeException，所以从事务方法抛出时符合默认回滚条件。并不是“只要程序任何地方出错，刚才所有数据库变化都会回滚”，必须考虑异常类型、捕获位置和事务是否仍然存在。

    默认传播方式 REQUIRED 的意思是：存在合适的当前事务就加入，否则创建。外层事务内调用普通查询，通常仍使用绑定在当前线程的数据库资源，不需要每个辅助方法都加事务注解。事务正常结束时真正提交的是数据库资源上的修改，不是把 Java 对象变回初始状态；已经填入实体的 ID 也不会因回滚自动改回 null。

    同类调用的常见误解

    Spring 常通过代理在方法入口前后执行事务逻辑。Controller 调用容器提供的 service.create，会经过代理。而同一个对象内部调用 this.someMethod，通常不会再次经过这个代理，因此内部方法上的事务注解不能被当作一定会重新生效。当前 create 调用 find 并没有问题：create 已经建立了外层事务，find 只是参与其中的普通辅助调用。

    真正容易出错的情形是：外部调用一个没有事务的方法，它内部再调用同类的 @Transactional 方法，并期待此时创建新事务。默认代理模式下，这个期待通常不成立。本项目模拟器把数据库批次操作放到独立的 SimulationBatchService，调度服务通过注入的 Bean 调用它，使调用穿过事务代理。你可以由此理解分开类的实际理由，而不只把它视为目录风格。

    事务与 HTTP 成功不是同一瞬间

    Service 方法完成并通过代理提交后，Controller 还需要构造响应，框架还需要序列化和发送。假如传输时网络断了，客户端看到失败或超时，数据库却可能已经提交。事务不能把网络传输和浏览器状态也变成同一个原子操作。是否安全重试需要根据接口设计判断，不能把所有 POST 都盲目重发。

    同理，数据库事务不会自动撤销文件系统写入。本项目图片上传另外使用文件补偿逻辑处理失败，不能仅靠数据库回滚删除已经落盘的文件。学习新增品类时先掌握纯数据库事务；接触图片、消息或第三方调用时，再检查它们是否真的受同一事务管理器控制。

    怎样证明事务有效

    不要只看方法上有没有注解。有效验证是在可控测试环境里令中途失败，再查询数据库确认前面的写入也没有留下。项目现有测试包含批量修改和图片失败场景，但你应阅读具体断言，弄清它们验证的是哪种回滚。测试方法自身的事务也可能影响观察，要把应用事务的失败语义和测试结束后的清理分开。

    本章原理可对照 Spring 的事务注解文档。阅读文档时注意版本和代理模式，先理解当前项目实际采用的路径，再研究更复杂的传播级别或隔离级别；不要在没有具体问题时随意更改这些选项。

    删除：业务判断与外键需要共同考虑

    // 项目原方法，位于 CategoryService
@Transactional
public void delete(long id) {
    find(id);
    if (mapper.references(id) > 0) {
        throw new BusinessException(409,
            "该品类仍被商品使用，请先调整商品分类");
    }
    mapper.unlinkDeletedProducts(id);
    mapper.delete(id);
}

    先检查品类存在，再统计未删除商品。仍被有效商品使用就拒绝。没有有效引用后，还要把已逻辑删除商品的 category_id 设为 NULL，最后删除品类。这一步解除历史引用是必要的：外键只看到数据库中还有行引用它，不会因为你的业务字段 deleted=1 就自动忽略那行。V3 的可空调整正是为这一步提供结构支持。

    解除引用和删除品类放在同一个事务，避免只解除了一半或后续失败时留下不符合预期的结果。Controller 返回 void 配合 @ResponseStatus(NO_CONTENT)，因此成功是 204 且响应体为空。前端 api.js 特别检查 204 后直接返回 null，而不是继续解析不存在的 JSON。

    package com.yl.clothing.service;

import com.yl.clothing.common.Checks;
import com.yl.clothing.common.PageResult;
import com.yl.clothing.converter.ProductConverter;
import com.yl.clothing.dto.*;
import com.yl.clothing.entity.Product;
import com.yl.clothing.entity.ProductColor;
import com.yl.clothing.exception.BusinessException;
import com.yl.clothing.mapper.ProductMapper;
import com.yl.clothing.vo.*;
import java.math.BigDecimal;
import java.util.HashSet;
import java.util.List;
import java.util.Set;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ProductService {
    private final ProductMapper mapper;
    private final CategoryService categories;

    public ProductService(ProductMapper mapper, CategoryService categories) {
        this.mapper = mapper;
        this.categories = categories;
    }

    public PageResult<ProductVO> list(String keyword, Long categoryId, Long channelId, Boolean onSale, int page, int pageSize) {
        Checks.pagination(page, pageSize);
        var query = new ProductQuery(keyword, categoryId, channelId, onSale, pageSize, (page - 1) * pageSize);
        return new PageResult<>(mapper.list(query).stream().map(ProductConverter::product).toList(),
                mapper.count(query), page, pageSize);
    }

    public ProductDetailVO find(long id) {
        var product = Checks.require(mapper.find(id), "商品");
        var colors = mapper.colors(id).stream()
                .map(color -> ProductConverter.colorDetail(color,
                        mapper.images(color.getId()).stream().map(ProductConverter::image).toList()))
                .toList();
        return ProductConverter.detail(product, colors);
    }

    @Transactional
    public ProductDetailVO create(ProductCreateRequest value) {
        categories.find(value.categoryId());
        Product product = new Product();
        product.setCode(value.code().strip());
        product.setName(value.name().strip());
        product.setCategoryId(value.categoryId());
        product.setDescription(value.description() == null ? "" : value.description());
        mapper.insert(product);
        return find(product.getId());
    }

    @Transactional
    public ProductDetailVO update(long id, ProductPatchRequest value) {
        find(id);
        if (value.categoryId() != null) {
            categories.find(value.categoryId());
        }
        if (value.name() == null && value.code() == null && value.description() == null && value.categoryId() == null) {
            throw new BusinessException(400, "请提供需要修改的字段");
        }
        mapper.update(id, value);
        return find(id);
    }

    @Transactional
    public void delete(long id) {
        find(id);
        mapper.delete(id);
    }

    public ColorVO color(long id) {
        return ProductConverter.color(Checks.require(mapper.color(id), "配色"));
    }

    @Transactional
    public ColorVO createColor(long productId, ColorCreateRequest value) {
        find(productId);
        ProductColor color = new ProductColor();
        color.setProductId(productId);
        color.setName(value.name().strip());
        color.setHex1(value.hex1());
        color.setHex2(value.hex2());
        mapper.insertColor(color);
        mapper.createSkus(color.getId());
        mapper.createListings(color.getId(), value.initialPrice());
        return color(color.getId());
    }

    @Transactional
    public ColorVO updateColor(long id, ColorPatchRequest value) {
        color(id);
        mapper.updateColor(id, value);
        return color(id);
    }

    @Transactional
    public void deleteColor(long id) {
        color(id);
        mapper.deleteColor(id);
    }

    public PageResult<ListingVO> listings(long productId, Long colorId, Long channelId, String size,
                                         Boolean onSale, int page, int pageSize) {
        Checks.pagination(page, pageSize);
        Checks.require(mapper.find(productId), "商品");
        if (size != null && !Set.of("S", "M", "L", "XL", "XXL").contains(size)) {
            throw new BusinessException(400, "尺码只能为 S、M、L、XL、XXL");
        }
        var query = new ListingQuery(productId, colorId, channelId, size, onSale, pageSize, (page - 1) * pageSize);
        return new PageResult<>(mapper.listings(query).stream().map(ProductConverter::listing).toList(),
                mapper.listingCount(query), page, pageSize);
    }

    @Transactional
    public List<ListingVO> updateListings(List<Long> ids, BigDecimal price, Boolean onSale) {
        if (price == null && onSale == null) {
            throw new BusinessException(400, "请提供价格或销售状态");
        }
        if (new HashSet<>(ids).size() != ids.size()) {
            throw new BusinessException(400, "销售记录不能重复");
        }
        ids.forEach(id -> Checks.require(mapper.listing(id), "销售记录"));
        int updated = mapper.updateListings(ids, price, onSale);
        if (updated != ids.size()) {
            throw new BusinessException(409, "商品状态已变化，请刷新后重试；本次修改已回滚");
        }
        return ids.stream().map(mapper::listing).map(ProductConverter::listing).toList();
    }
}

            if (clazz.isArray()) assertTyped(clazz.getComponentType());
        } else if (type instanceof ParameterizedType parameterized) {
            assertTyped(parameterized.getRawType());
            for (Type argument : parameterized.getActualTypeArguments()) assertTyped(argument);
        } else {
            throw new AssertionError("Unresolved business type: " + type);
        }
    }
}

    术语速查

    HTTP / REST
    HTTP 是请求响应协议；REST 是围绕资源组织接口的一种设计风格。路径与状态的具体约定仍需要项目定义。
    Bean / IoC / DI
    Bean 是容器管理的对象；IoC 强调把组装控制交给容器；DI 是注入依赖的方式。
    MVC / DispatcherServlet
    MVC 分离处理职责；DispatcherServlet 是 Spring MVC 协调请求处理的入口组件。
    DTO / Entity / VO
    DTO 表达输入或数据传输；本项目 Entity 表达持久化数据；VO 表达对外输出。命名本身不自动提供框架行为。
    Projection / Converter
    Projection 承载专门查询的结果；Converter 显式转换不同模型，不等同于 JSON 序列化。
    Mapper / JDBC / 连接池
    Mapper 将方法对应到 SQL；JDBC 是 Java 数据库访问 API；连接池管理可复用数据库连接。
    classpath
    运行时查找类和资源的路径集合。resources 下的内容进入类路径，不以源码目录名作为前缀。
    record / 泛型 / Stream
    record 简化数据载体；泛型保留类型约束；Stream 提供数据处理管道，map 是逐项转换操作。
    序列化 / 反序列化
    本项目中分别指 Java 对象转 JSON 和 JSON 转 Java 对象，由 Jackson 参与完成。
    事务 / 回滚 / 代理
    事务组织数据库工作单元；回滚撤销未提交数据库变化；代理在方法调用前后加入事务等处理。
    迁移 / Profile
    迁移记录数据库结构变化；Profile 选择特定运行配置，如独立测试库。
    MockMvc / 契约测试
    MockMvc 模拟 MVC 请求处理；契约测试保护状态、字段和类型等外部约定。
    幂等 / 重试
    幂等关注重复执行对结果的影响；客户端超时不证明服务端没有提交，重试策略需要结合操作设计。
